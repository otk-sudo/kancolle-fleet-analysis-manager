# 開発ルール・コーディング規約

迷ったときは「初学者が読んで理解できるか」を基準に判断する。

※ 自動整形（Spotless・Prettier）と依存ルールの自動チェック（ArchUnit）は、このルールの合意後に別のPRで導入する。

## 0. 初学者でもわかるように書く（最優先）
このプロジェクトは初めて使う技術が多いため、初学者が読んで理解できることを最優先にする。
- ファイルの中で、ある技術・アノテーション・設定が初めて出てくるところに「それは何か」「なぜ使うか」を1〜2行で書く
  - 例: `@SpringBootApplication // Spring Bootアプリの起点。設定の自動読み込みと部品（Bean）の自動登録を有効にする`
- 各ディレクトリに README.md を置き、役割・使っている技術・最初に読むファイルを書く
- 用語は [用語集](guide/用語集.md) にまとめ、初出の用語はそこへリンクする
- 処理の流れ（リクエストがどこを通るか）は [はじめに](guide/はじめに.md) に図で書く
- 略語や業界用語は避けるか、初出で説明する
- PRの説明には「このPRで初めて出てくる技術」と「手元での試し方」を書く
- 賢い書き方より読みやすい書き方を選ぶ（ストリームの多段チェーンや三項演算子の入れ子より、素直なfor文やif文）

## 1. 言語
- コメント、ドキュメント、コミットメッセージ、PRは日本語で書く
- クラス名・メソッド名・変数名などの識別子は英語
- テストメソッド名は日本語でよい（何を確かめるテストかを文章で書く。例: `同じ種なら同じ結果になる`）

## 2. コメント
- 「なぜそうしたか」を書く。「何をしているか」はコードで読めるように書き、コメントで繰り返さない
  - 良い例: `// java.util.Randomは近い種どうしで最初の乱数が似通うため、SplittableRandomを使う`
  - 悪い例: `// 乱数を生成する`
- public なクラス・メソッドには Javadoc / TSDoc を1〜2行で書く（役割と、仕様書の該当箇所があればその番号）
- 仕様に由来する決まりごとは、仕様書の節番号を添える（例: `// 仕様 6.3: 当選したら落選回数をリセット`）
- TODOは `// TODO(段階N): 内容` の形で、いつやるかを書く
- 自動生成コード（`build/generated`、`schema.gen.ts`）は編集しない。直したいときは `api/openapi.yaml` を直す

## 3. Java
- フォーマット: Spotless + palantir-java-format（インデント4スペース）。`./gradlew spotlessApply` で自動整形し、CIで `spotlessCheck` を行う
- 層の依存ルール
  - `domain` は Spring・AWS・Jackson などに依存しない（純粋なJava）
  - `infra` は `domain` に依存してよい、`app` は両方に依存してよい。逆向きは禁止
  - ArchUnit のテストでこのルールを自動チェックする
- 値は不変（record・final）を基本にする。null は返さず `Optional` か空のコレクションを返す
- 設定で変えられる値（選択肢、ステータス、条件、抽選の重み）はコードに直書きしない（仕様 10章）
- 例外: 業務上のエラーは専用の例外クラスにし、API層で `ApiError` に変換する

## 4. TypeScript / React
- Lint: oxlint、フォーマット: Prettier。CIで両方チェックする
- `strict` を有効にし、`any` は使わない
- APIの型は生成した型を使い、手で書かない
- コンポーネントは関数コンポーネント。1ファイル1コンポーネント

## 5. API（OpenAPI）
- APIを変えるときは、まず `api/openapi.yaml` を変更し、そこからコードを生成する
- 配信用画面向けのレスポンスに、XのIDや課金額を含めない（仕様 7.2）
- 既存の項目の削除・型変更は、画面側の対応と同じPRで行う

## 6. テスト
- `domain` の業務ロジック（重複判定、条件ルール、抽選、ステータス遷移）は単体テスト必須
- バグを直すときは、先にそのバグを再現するテストを書く
- テストを無効化・スキップしてCIを通すことはしない
- DynamoDB を使うテスト（`backend/infra` の `infra/dynamodb/`）は DynamoDB Local を使う。DynamoDB Local が中で使う部品（SQLite）が Linux（x86_64）・Windows（64bit）・Intel の Mac 用しか配られていないため、Apple シリコンの Mac や ARM の Linux では `./gradlew build` のテストが失敗する。その場合は GitHub Codespaces で動かすか、CI の結果で確かめる

## 7. Git・PR
- `main` へ直接プッシュしない。ブランチを切ってPRを出す
  - ブランチ名: `feature/内容`、`fix/内容`、`docs/内容`（Claudeが作るものは `claude/内容`）
- コミットメッセージ: 1行目に `種別: 要約`（種別は feat / fix / docs / refactor / test / chore）、必要なら空行のあとに理由
- レビューの流れ
  1. PRを出し、CIがすべて成功するまで直す
  2. レビューエージェント（Claude）がコードレビューを行い、指摘を直してCIを再度通す
  3. 開発者（OTさん）が最終確認をしてマージする
- マージ方法は Squash merge（PRのコミットを1つにまとめて main に入れる）
- 1つのPRは1つの目的に絞る（段階ごと、機能ごと）

## 8. 秘密情報・個人情報
- APIキー、フォーム用の秘密キー、AWSの認証情報はコミットしない（`.env` は .gitignore 済み）
- テストデータに実在の応募者のXのIDを使わない
