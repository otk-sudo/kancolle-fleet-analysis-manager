## 1. リポジトリ構成（モノレポ）

```
/
├─ api/                 OpenAPI定義（openapi.yaml）。ここが唯一の正
├─ backend/             Java 21 / Spring Boot 4 / Gradle
│  ├─ app/              Lambdaのエントリポイント、API層（生成インターフェースの実装）
│  ├─ domain/           業務ロジック（重複判定、条件ルール、抽選、ステータス遷移）。外部依存なし
│  └─ infra/            DynamoDBアクセス、Cognito連携
├─ frontend/            React + TypeScript（Vite）。APIクライアントはopenapi.yamlから生成
├─ infra/               AWS CDK（Java）
├─ gas/                 Googleフォーム連携のApps Script
├─ docs/                仕様書・設計メモ
└─ .github/workflows/   CI
```

- Gradleはマルチプロジェクト（backend/app, backend/domain, backend/infra, infra）
- サーバー側の生成: openapi-generator の Spring インターフェース生成（`interfaceOnly`）
- 画面側の生成: openapi-typescript ＋ openapi-fetch
- domain は Spring にも AWS にも依存させず、単体テストで中身を固める

## 2. データモデル（DynamoDB 単一テーブル）

テーブル名: `Main`。キーは `PK` / `SK`、検索用に GSI1・GSI2。

| エンティティ | PK | SK | 主な属性 |
|---|---|---|---|
| 応募 | `APP#<applicationId>` | `META` | xId（正規化済み）、提督名、匿名希望、シミュレータURL、回答（formVersion付きのmap）、ステータス、ステータス変更日時、並び順キー、配信日、メモ、見送りの理由、分析メモ、配信アーカイブURL、印（重複/再応募/条件外と理由）、受付日時、版（同時変更の検知用） |
| 回答IDの控え | `SUB#<フォームの回答ID>` | `META` | 応募ID。同じ回答を二重に登録しないよう、「まだないか、同じ応募IDのときだけ書く」条件付きで、応募を初めて保存するときに一緒に書く（トランザクション） |
| 変更履歴 | `APP#<applicationId>` | `HISTORY#<日時>#<順番>#<履歴ID>` | 種類（ステータスの変更／XのIDの修正）、変更前、変更後、実行者、補足（見送りの理由、どの操作で変わったか）。応募と同じトランザクションで書く |
| 抽選記録 | `LOTTERY#<lotteryId>` | `META` | 日時、実行者、方式（まとめ/配信中）、当選人数、乱数の種、取り消し（日時・実行者）、対象者ごとの当たりやすさと結果（entries。1件のアイテムは最大400KBで、対象者1人分は100バイトほどなので数千人でも収まる） |
| 設定 | `SETTINGS` | `<種類>`（OPTIONS, STATUSES, RULES, LOTTERY） | 設定内容、版 |
| 閲覧専用URLの鍵 | `STREAM` | `TOKEN` | 鍵のハッシュ値、発行日時。設定API（/settings）からは読み書きできず、/stream/token でだけ変える |
| 配信の操作の許可 | `STREAM` | `OPERATOR#<userId>` | 配信の操作を許可した関係者 |
| 配信の操作履歴 | `STREAM` | `OP#<日時>` | 「次の人へ」「中断」の前後の状態（「元に戻す」に使う。1回分だけ使う） |
| 操作履歴 | `AUDIT#<yyyy-mm>` | `<日時>#<id>` | 操作種別、対象、実行者 |

GSI:
- GSI1（ステータス別の並び）: `GSI1PK = STATUS#<ステータス>`、`GSI1SK = <並び順キー>`。次に分析する人・一覧の絞り込みに使う
- GSI2（種類ごとの一覧）: 応募は `GSI2PK = APPS`、`GSI2SK = <受付日時>#<applicationId>`（受付順）。抽選記録は `GSI2PK = LOTTERIES`、`GSI2SK = <実行日時>#<lotteryId>`（新しい順に読む）。日時は秒の端数を9桁までそろえて書く（文字列の順が日時の順になるように）
- GSI3（同じ応募者の応募）: `GSI3PK = XID#<xId>`、`GSI3SK = <受付日時>`。重複・再応募の判定と履歴に使う。XのIDを直すと、応募の xId を書き換えるだけで自動的に付け替わる

応募者ごとの「落選回数」や「最終当選日時」は保存しない。GSI3で同じ人の応募と抽選の結果を集めて毎回数え直す（1人の応募は多くても数十件なので速さは問題にならない）。保存しておくと、抽選の取り消しやXのIDの修正のたびに直す必要があり、ずれの原因になるため。

並び順キー: 受付時は受付日時から作り、手動で並べ替えたら前後のキーの間の値を入れる（全件の振り直しが不要。動かした1件だけ保存するので、動かしていない応募の版は変わらない）。間に入る数がなくなったときだけ、そのグループを振り直す。ほかのステータスから移ってきたときは最後尾（中断のときは先頭）のキーを入れる。

版（同時変更の検知）: 応募は版の番号を持ち、保存のたびに1増える。保存は「読み込んだときと版が同じとき」だけ行う条件付き書き込みにし、違えば（ほかの人が先に保存していれば）409にする。画面は読み込んだときの版を送る。段階1で保存した応募には版がないので、読み込むと版1として扱う。

まとめての保存: 1回の操作で変わる応募（本人、印が変わった同じ人の応募、まとめて変えた応募）は1つのトランザクションで保存する（全部か何もしないか）。トランザクションは最大100件の書き込みなので（公式: https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html ）、まとめてのステータス変更は1回25件までにしている（1件につき応募と履歴の2件、さらに印が変わった同じ人の応募も書くため。それでも超えたら何も保存せず断る）。抽選は対象者が多いので1件ずつ保存する。抽選記録を先に保存し、途中でほかの人の変更とぶつかった応募は読み直してやり直す（段階6の取り消しと合わせて見直す）。

GSI（索引）からの読み込みは結果整合性（保存の直後、1秒未満は反映されていないことがある）。索引の中身をそのまま使うと、直前に変えたステータスが古いまま見え、それを保存し直して変更を消してしまうので、一覧・同じ人の応募の検索では索引でキーだけを調べ、中身は本体から強い整合性で読み直す（BatchGetItem）。それでも、保存した直後の新しい応募が一覧に出てこない（重複の印がつかない）ことはまれにある。印は同じ人の応募が次に変わったときの付け直しで直り、古い内容での上書きは版（同時変更の検知）で防ぐ。

保存先の切り替え: 設定 `app.storage` が `memory` ならメモリ（試作・テスト用）、`dynamodb` なら DynamoDB。手元では `local` プロファイルで DynamoDB Local（公式の Maven 版。`./gradlew :backend:infra:runDynamoDbLocal` でポート8000に起動）を使う。テストでは DynamoDB Local をテストと同じプログラムの中で動かす。

規模の想定: 応募は数百〜数千件。一覧は1回のクエリで取れる範囲に収まる。

### ログインと権限（段階3）

- 「誰か」（認証）は、ログインで受け取ったトークン（JWT）で確かめる。画面は API を呼ぶたびにトークンを `Authorization: Bearer ...` ヘッダーに付けて送る。トークンがない・期限切れ・偽物なら 401
- 「何をしてよいか」（認可）は、役割ごとの決まり（`backend/domain` の `AccessPolicy`）で決め、各コントローラーの最初で確かめる。できないことなら 403。決まりは Spring や AWS に依存しないので、ログインの方法が変わっても同じものを使う
- 二段階認証（MFA）が必要な役割（配信者・運営）で、まだ設定していない人は、何もできない（画面は設定を求める案内だけを出す）
- 関係者への配信の操作の許可は、DynamoDB の `STREAM` / `OPERATOR#<userId>` に保存し、リクエストのたびに読む（許可を取り消したら、次の操作から断られる）
- トークンの出し手は設定 `app.auth.mode` で切り替える
  - `dev`（手元の demo プロファイル・テスト）: 仮ログイン。`/dev/users` の試しユーザーを選ぶと、バックエンドが起動のたびに作る鍵で署名したトークンを出す（12時間有効。再起動すると前のトークンは使えなくなる）
  - `cognito`（設定がないときもこちら）: Cognito のトークン。段階4で作るので、今は起動できないようにしている（うっかり仮ログインのまま公開しないため）
- トークンの中身は Cognito に合わせて `sub`（ユーザーID）、`name`（表示名）、`cognito:groups`（役割のグループ）を読む。段階4で Cognito の実際のトークンの項目名を公式の資料で確かめる（今は未確認）
- 画面では、できない操作のボタンや入力欄を出さない（`/me` の permissions を見る）。これは使いやすさのためで、本当の確認はバックエンドが毎回行う

## 4. 業務ロジックの要点

- 重複・再応募の判定は受付時に行い、印として保存する。同じ人のほかの応募のステータスやXのIDが変わったときにも付け直す（判定ルールを変えたら全件の再判定を実行できる）
- 印は「自分より前に受け付けた同じ人の応募」だけを見て決める。重複 = 自分がまだ終わっていなくて、前にまだ終わっていない応募がある。再応募 = 前に終わった応募（分析済み・見送り・落選）がある。Apps Script の再送で古い回答があとから届いても、受付日時（回答した日時）の順で決まる
- 抽選の重み: `weight = 1 + 落選回数 × 補正の強さ`（補正オフなら常に1）。重み付き非復元抽出
- 乱数の種は抽選ごとに生成して記録する。同じ種と対象者なら同じ結果が再現できる
- ステータス遷移は表で定義し、許されない遷移はエラーにする。「落選」へは抽選からだけ変えられる。抽選・「次の人へ」・重複の解消など仕組みが行う変更は、手で変えるときの表とは別の入口（`changeStatusBySystem`）を通す
- 同時に変更されたときは、応募の版を比べて後から来た変更を409にする（DynamoDBの条件付き書き込み）
- 閲覧専用URLの鍵は、推測できない十分に長いランダムな値にし、保存するのはハッシュ値だけにする（漏れても元の鍵がわからないように）

## 5. 開発の進め方（段階）

| 段階 | 内容 | できるようになること |
|---|---|---|
| 0. 土台 | リポジトリ、Gradleマルチプロジェクト、openapi.yaml、コード生成、CI | ビルドとテストが自動で回る |
| 1. 受付と一覧 | 受付API、Apps Script、一覧・詳細API、DynamoDB、ローカル実行（DynamoDB Local） | フォームの応募がツールに入って一覧で見える |
| 2. 進捗管理 | ステータス変更、並べ替え、重複・再応募の印（付け直しを含む）、重複の解消、検索・まとめて変更、見送りの理由、XのIDの修正、同時変更の検知、履歴比較（前回分析した応募と）、分析メモ・アーカイブURL | 課題1・2が解決する |
| 3. 画面とログイン | React管理画面のデザインの作り込み（画面の見た目・使いやすさ。配信者さんの意見を反映）、Cognito（配信者・運営はMFA）、権限、関係者への配信の操作の許可 | 配信者・関係者が使い始められる |
| 4. AWS公開 | CDKでLambda/API Gateway/DynamoDB/S3/CloudFront/Cognito、Budgets、DynamoDBのバックアップ、フォーム用秘密キーの再発行手順 | 本番運用できる |
| 5. 配信 | 表示専用の配信用画面と閲覧専用URL、配信の操作パネル（次の人へ・中断・元に戻す。PCの別タブで使う）、デザインの作り込み（配信に映したときの見栄え）、匿名表示 | 配信で使える |
| 6. 抽選 | まとめ抽選（確認画面）、配信中の抽選、落選補正、記録、一番新しい抽選の取り消し | 応募が多くても回せる |
| 7. 設定と取り込み | 条件ルール、選択肢、ユーザー管理、CSV取り込み、削除依頼の画面（確認・控えの削除手順の表示） | 運用を配信者さんに任せられる |

各段階で動くものを作り、段階1〜3あたりで一度配信者さんに見てもらう。

試作版（PR #2）の画面は動きを確かめるための仮のデザインで、見た目は段階3（管理画面）と段階5（配信用画面）で作り込む。デザインの決まりと理由は [ui/design-plan.md](ui/design-plan.md)、実装するときのお願いは [ui/handoff.md](ui/handoff.md)（どちらも共有フォルダの design/ の写し。各画面のデザイン案はキャンバス https://claude.ai/artifact/VW24xQAhzirbp57T96TUGM ）。管理画面（一覧・詳細・抽選・設定の抽選）は段階3で対応済み。

ログインは段階3では手元で試すための仮ログイン（試しユーザーを選ぶだけ）にし、本物の Cognito は段階4で AWS に作るときに確かめる（2026-10-03 に決定。理由: 手元で動く公式の Cognito の代わりが見つからず、段階4の前に AWS の準備をしなくて済むため）。権限の確認は、仮ログインでも Cognito でも同じ道を通るので、段階4ではトークンの出し手だけを差し替える。

仕様 v1.1（運用目線の見直し）で、試作版と違うところ（各段階で直す）:
- 試作版の配信用画面にはボタンがあるが、v1.1では表示専用にして操作パネルを分ける（段階5）
- 試作版は比較の相手が「前回の応募」だが、v1.1では「前回分析した応募」（段階2で対応済み）
- 試作版は重複の印が受付時のまま変わらないが、v1.1では同じ人のほかの応募が変わるたびに付け直す（段階2で対応済み）
- 試作版は手で「落選」にできるが、v1.1では抽選でだけ付く（段階2で対応済み）
- 試作版の「次の人へ」は分析予定・未着手の選び方（印の扱い、抽選オンのとき未着手を選ばない）はv1.1と同じ。同時の操作の検知と「元に戻す」はまだない（段階5）
