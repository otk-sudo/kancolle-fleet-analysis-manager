## 1. リポジトリ構成（モノレポ）

```
/
├─ api/                 OpenAPI定義（openapi.yaml）。ここが唯一の正
├─ backend/             Java 21 / Spring Boot 4 / Gradle
│  ├─ app/              起動の入口、API層（生成インターフェースの実装）
│  ├─ domain/           業務ロジック（重複判定、条件ルール、抽選、ステータス遷移）。外部依存なし
│  └─ infra/            データの保存（今は DynamoDB とメモリ。v1.2 で SQLite に変える）
├─ frontend/            React + TypeScript（Vite）。APIクライアントはopenapi.yamlから生成
├─ gas/                 Googleフォーム連携のApps Script（v1.2 でウェブアプリに変える）
├─ docs/                仕様書・設計メモ
└─ .github/workflows/   CI
```

- Gradleはマルチプロジェクト（backend/app, backend/domain, backend/infra）。AWS CDK（infra/）は v1.2 で作らないことにした
- サーバー側の生成: openapi-generator の Spring インターフェース生成（`interfaceOnly`）
- 画面側の生成: openapi-typescript ＋ openapi-fetch
- domain は Spring にも AWS にも依存させず、単体テストで中身を固める

### v1.2 で使うもの（2026-10-03 に公式の資料で確かめた）

**データベース: SQLite**
- データベース全体が1つのファイルで、別のPCにコピーしても使える。ファイルの形式は、これからの版でも読めると約束されている（公式: https://www.sqlite.org/onefile.html ）
- バックアップや、配信者さんのPCを替えるときの引っ越しがしやすい
- Java からは JDBC ドライバーで使う。ドライバーは SQLite の公式のものではないので、段階4で選ぶときに確かめる
- H2（Java だけで動くデータベース）も候補だった。ただ、版を上げるとファイルの移し替えが要ることがある（公式: https://www.h2database.com/html/migration-to-v2.html ）ので、SQLite にする
- PostgreSQL（開発者が仕事で使うデータベース）も一度選んだが、2026-10-03 にOTさんが「配信者さん第一」で SQLite に決めた。PostgreSQL をツールに入れると、ダウンロードが大きくなる、大きな版を上げるときにデータの移し替えが要る（公式: https://www.postgresql.org/docs/current/upgrading.html ）、裏で別のプログラムが動き、止まる原因が増える、と配信者さんの負担が増えるため。SQLite は、1人で使うデスクトップアプリのデータの置き場所として使うのが、公式に挙げられている使い方（公式: https://www.sqlite.org/whentouse.html ）
- バックアップの写しは `VACUUM INTO`（データベースの中身を別のファイルに書き出す命令）で作る。使用中のデータベースからでも、ある時点のそろった写しができる（公式: https://www.sqlite.org/lang_vacuum.html ）。ファイルをそのままコピーすると、書き込み途中の内容が抜けることがあるので使わない
- バックアップから戻すときは、データベースへの接続をすべて閉じ、ファイルを入れ替えてから開き直す
- 同時変更の検知（版）は、`UPDATE ... WHERE version = ?`（読み込んだときの版と同じときだけ更新する）で行う

**配布: jpackage**
- Windows のインストーラー（exe か msi）を作る。Java の実行環境が中に入るので、配信者さんが Java を入れなくてよい（公式: https://docs.oracle.com/en/java/javase/21/jpackage/packaging-overview.html ）
- インストーラーは Windows の上で作る必要があり、WiX という道具が要る（同じページ）。GitHub Actions の Windows の環境で作るつもり。WiX が入っているか、どの版の WiX が要るかは未確認
- データのファイルは、インストール先ではなく利用者ごとのデータのフォルダに置く（入れ直しで消えないように）

**フォーム連携: Apps Script のウェブアプリ**
- `doPost`（POST で呼ばれたときに動く関数）で秘密キーを確かめてから、フォームの回答を JSON で返す（公式: https://developers.google.com/apps-script/guides/web ）
- 応答は script.googleusercontent.com へ転送されるので、ツールの HTTP の部品は転送をたどる設定にする（公式: https://developers.google.com/apps-script/guides/content ）
- 細かい決まりは仕様の3章

**ほかのサイトからの攻撃を防ぐ（ログインがないため）**
- ツールの中の Web サーバーは 127.0.0.1（そのPCの中からだけ届く住所。「ループバック」と呼ぶ）でだけ待ち受ける。ほかのPCからつながらないようにするため
- `Host` ヘッダー（どのアドレスあてに送ったか）が `127.0.0.1:<ポート>` か `localhost:<ポート>` でない要求は断る。DNSリバインディング（ほかのサイトが、自分の名前でこのPCのツールにつないでデータを読む攻撃）を防ぐため
- データを変える要求（POST・PUT・PATCH・DELETE）は、`Origin` ヘッダー（どのサイトの画面から送ったか）がツール自身のときだけ受け付ける。CSRF（ほかのサイトが、裏で削除などの命令を送る攻撃）を防ぐため
- 送る内容は JSON だけを受け付け、ほかのサイトからの呼び出しを許す CORS の設定はしない
- すべての応答に `X-Frame-Options: DENY` と `Content-Security-Policy: frame-ancestors 'none'` を付け、ツールの画面をほかのページの中（iframe）に表示させない。ほかのサイトが画面を透明にして重ね、ボタンを押させる攻撃（クリックジャッキング）を防ぐため（公式: https://developer.mozilla.org/docs/Web/HTTP/Reference/Headers/X-Frame-Options ）

## 2. データモデル（DynamoDB 単一テーブル）

テーブル名: `Main`。キーは `PK` / `SK`、検索用に GSI1・GSI2。

| エンティティ | PK | SK | 主な属性 |
|---|---|---|---|
| 応募 | `APP#<applicationId>` | `META` | xId（正規化済み）、提督名、匿名希望、シミュレータURL、回答（formVersion付きのmap）、ステータス、ステータス変更日時、並び順キー、配信日、メモ、見送りの理由、分析メモ、配信アーカイブURL、印（重複/再応募/条件外と理由）、受付日時、版（同時変更の検知用） |
| 回答IDの控え | `SUB#<フォームの回答ID>` | `META` | 応募ID。同じ回答を二重に登録しないよう、「まだないか、同じ応募IDのときだけ書く」条件付きで、応募を初めて保存するときに一緒に書く（トランザクション） |
| 変更履歴 | `APP#<applicationId>` | `HISTORY#<日時>#<順番>#<履歴ID>` | 種類（ステータスの変更／XのIDの修正）、変更前、変更後、実行者、補足（見送りの理由、どの操作で変わったか）。応募と同じトランザクションで書く |
| 抽選記録 | `LOTTERY#<lotteryId>` | `META` | 日時、実行者、方式（まとめ/配信中）、当選人数、乱数の種、取り消し（日時・実行者）、対象者ごとの当たりやすさと結果（entries。1件のアイテムは最大400KBで、対象者1人分は100バイトほどなので数千人でも収まる） |
| 設定 | `SETTINGS` | `<種類>`（OPTIONS, STATUSES, RULES, LOTTERY） | 設定内容、版 |
| 閲覧専用URLの鍵 | `STREAM` | `TOKEN` | 鍵のハッシュ値、発行日時。設定API（/settings）からは読み書きできず、/stream/token でだけ変える |
| 配信の操作の許可 | `STREAM` | `OPERATOR#<userId>` | 配信の操作を許可した関係者 |
| 配信の操作履歴 | `STREAM` | `OP#<日時>` | 「次の人へ」「中断」の前後の状態（「元に戻す」に使う。1回分だけ使う） |
| 操作履歴 | `AUDIT#<yyyy-mm>` | `<日時>#<id>` | 操作種別、対象、実行者 |

GSI:
- GSI1（ステータス別の並び）: `GSI1PK = STATUS#<ステータス>`、`GSI1SK = <並び順キー>`。次に分析する人・一覧の絞り込みに使う
- GSI2（種類ごとの一覧）: 応募は `GSI2PK = APPS`、`GSI2SK = <受付日時>#<applicationId>`（受付順）。抽選記録は `GSI2PK = LOTTERIES`、`GSI2SK = <実行日時>#<lotteryId>`（新しい順に読む）。日時は秒の端数を9桁までそろえて書く（文字列の順が日時の順になるように）
- GSI3（同じ応募者の応募）: `GSI3PK = XID#<xId>`、`GSI3SK = <受付日時>`。重複・再応募の判定と履歴に使う。XのIDを直すと、応募の xId を書き換えるだけで自動的に付け替わる

応募者ごとの「落選回数」や「最終当選日時」は保存しない。GSI3で同じ人の応募と抽選の結果を集めて毎回数え直す（1人の応募は多くても数十件なので速さは問題にならない）。保存しておくと、抽選の取り消しやXのIDの修正のたびに直す必要があり、ずれの原因になるため。

並び順キー: 受付時は受付日時から作り、手動で並べ替えたら前後のキーの間の値を入れる（全件の振り直しが不要。動かした1件だけ保存するので、動かしていない応募の版は変わらない）。間に入る数がなくなったときだけ、そのグループを振り直す。ほかのステータスから移ってきたときは最後尾（中断のときは先頭）のキーを入れる。

版（同時変更の検知）: 応募は版の番号を持ち、保存のたびに1増える。保存は「読み込んだときと版が同じとき」だけ行う条件付き書き込みにし、違えば（ほかの人が先に保存していれば）409にする。画面は読み込んだときの版を送る。段階1で保存した応募には版がないので、読み込むと版1として扱う。

まとめての保存: 1回の操作で変わる応募（本人、印が変わった同じ人の応募、まとめて変えた応募）は1つのトランザクションで保存する（全部か何もしないか）。トランザクションは最大100件の書き込みなので（公式: https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html ）、まとめてのステータス変更は1回25件までにしている（1件につき応募と履歴の2件、さらに印が変わった同じ人の応募も書くため。それでも超えたら何も保存せず断る）。抽選は対象者が多いので1件ずつ保存する。抽選記録を先に保存し、途中でほかの人の変更とぶつかった応募は読み直してやり直す（段階8の取り消しと合わせて見直す）。

GSI（索引）からの読み込みは結果整合性（保存の直後、1秒未満は反映されていないことがある）。索引の中身をそのまま使うと、直前に変えたステータスが古いまま見え、それを保存し直して変更を消してしまうので、一覧・同じ人の応募の検索では索引でキーだけを調べ、中身は本体から強い整合性で読み直す（BatchGetItem）。それでも、保存した直後の新しい応募が一覧に出てこない（重複の印がつかない）ことはまれにある。印は同じ人の応募が次に変わったときの付け直しで直り、古い内容での上書きは版（同時変更の検知）で防ぐ。

保存先の切り替え: 設定 `app.storage` が `memory` ならメモリ（試作・テスト用）、`dynamodb` なら DynamoDB。手元では `local` プロファイルで DynamoDB Local（公式の Maven 版。`./gradlew :backend:infra:runDynamoDbLocal` でポート8000に起動）を使う。テストでは DynamoDB Local をテストと同じプログラムの中で動かす。

規模の想定: 応募は数百〜数千件。一覧は1回のクエリで取れる範囲に収まる。

v1.2 で増えるAPI（段階4〜6で、先に openapi.yaml に書く）:
- フォームの取り込み: 最後に取り込んだ日時と結果を見る、「今すぐ取り込む」

- バックアップ: 写しの一覧、今すぐ写しを作る、写しから戻す（ファイルを選ぶことも）、保存先の設定

## 4. 業務ロジックの要点

- 重複・再応募の判定は受付時に行い、印として保存する。同じ人のほかの応募のステータスやXのIDが変わったときにも付け直す（判定ルールを変えたら全件の再判定を実行できる）
- 印は「自分より前に受け付けた同じ人の応募」だけを見て決める。重複 = 自分がまだ終わっていなくて、前にまだ終わっていない応募がある。再応募 = 前に終わった応募（分析済み・見送り・落選）がある。取り込みやCSV取り込みで古い回答があとから入っても、受付日時（回答した日時）の順で決まる
- 抽選の重み: `weight = 1 + 落選回数 × 補正の強さ`（補正オフなら常に1）。重み付き非復元抽出
- 乱数の種は抽選ごとに生成して記録する。同じ種と対象者なら同じ結果が再現できる
- ステータス遷移は表で定義し、許されない遷移はエラーにする。「落選」へは抽選からだけ変えられる。抽選・「次の人へ」・重複の解消など仕組みが行う変更は、手で変えるときの表とは別の入口（`changeStatusBySystem`）を通す
- 同時に変更されたときは、応募の版を比べて後から来た変更を409にする（v1.1 は DynamoDB の条件付き書き込み。v1.2 は SQLite の `UPDATE ... WHERE version = ?`）
