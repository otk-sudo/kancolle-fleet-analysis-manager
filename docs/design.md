## 1. リポジトリ構成（モノレポ）

```
/
├─ api/                 OpenAPI定義（openapi.yaml）。ここが唯一の正
├─ backend/             Java 21 / Spring Boot 4 / Gradle
│  ├─ app/              起動の入口、API層（生成インターフェースの実装）
│  ├─ domain/           業務ロジック（重複判定、条件ルール、抽選、ステータス遷移）。外部依存なし
│  └─ infra/            データの保存（SQLite と、テスト用のメモリ）
├─ frontend/            React + TypeScript（Vite）。APIクライアントはopenapi.yamlから生成
├─ gas/                 Googleフォーム連携のApps Script（v1.2 でウェブアプリに変える）
├─ docs/                仕様書・設計メモ
└─ .github/workflows/   CI
```

- Gradleはマルチプロジェクト（backend/app, backend/domain, backend/infra）。AWS CDK（infra/）は v1.2 で作らないことにした
- サーバー側の生成: openapi-generator の Spring インターフェース生成（`interfaceOnly`）
- 画面側の生成: openapi-typescript ＋ openapi-fetch
- domain は Spring にも AWS にも依存させず、単体テストで中身を固める

### v1.2 で使うもの（2026-10-03 に公式の資料で確かめた）

**データベース: SQLite**
- データベース全体が1つのファイルで、別のPCにコピーしても使える。ファイルの形式は、これからの版でも読めると約束されている（公式: https://www.sqlite.org/onefile.html ）
- バックアップや、配信者さんのPCを替えるときの引っ越しがしやすい
- Java からは JDBC ドライバー（Java からデータベースを使うための部品）の sqlite-jdbc（https://github.com/xerial/sqlite-jdbc ）で使う。SQLite の公式のものではないが、Spring Boot が版を管理している部品の一覧に入っているので、Spring Boot の版に合わせて上げられる
- 表を作る・形を変えるのは Flyway（データベースの形の変更を、番号つきの SQL ファイルで順に当てる道具。配布元: https://repo1.maven.org/maven2/org/flywaydb/flyway-core/ 。公式の説明のページは、作業した環境から開けず未確認）。ツールの起動時に、まだ当てていない SQL ファイルだけを実行する。配信者さんが新しい版に上げたときも、データを残したまま表の形が新しくなる
- H2（Java だけで動くデータベース）も候補だった。ただ、版を上げるとファイルの移し替えが要ることがある（公式: https://www.h2database.com/html/migration-to-v2.html ）ので、SQLite にする
- PostgreSQL（開発者が仕事で使うデータベース）も一度選んだが、2026-10-03 にOTさんが「配信者さん第一」で SQLite に決めた。PostgreSQL をツールに入れると、ダウンロードが大きくなる、大きな版を上げるときにデータの移し替えが要る（公式: https://www.postgresql.org/docs/current/upgrading.html ）、裏で別のプログラムが動き、止まる原因が増える、と配信者さんの負担が増えるため。SQLite は、1人で使うデスクトップアプリのデータの置き場所として使うのが、公式に挙げられている使い方（公式: https://www.sqlite.org/whentouse.html ）
- バックアップの写しは `VACUUM INTO`（データベースの中身を別のファイルに書き出す命令）で作る。使用中のデータベースからでも、ある時点のそろった写しができる（公式: https://www.sqlite.org/lang_vacuum.html ）。ファイルをそのままコピーすると、書き込み途中の内容が抜けることがあるので使わない
- バックアップから戻すときは、データベースへの接続をすべて閉じ、ファイルを入れ替えてから開き直す
- 同時変更の検知（版）は、`UPDATE ... WHERE version = ?`（読み込んだときの版と同じときだけ更新する）で行う

**配布: jpackage**
- Windows のインストーラー（exe か msi）を作る。Java の実行環境が中に入るので、配信者さんが Java を入れなくてよい（公式: https://docs.oracle.com/en/java/javase/21/jpackage/packaging-overview.html ）
- インストーラーは Windows の上で作る必要があり、WiX という道具が要る（同じページ）。GitHub Actions の Windows の環境で作るつもり。WiX が入っているか、どの版の WiX が要るかは未確認
- データのファイルは、インストール先ではなく利用者ごとのデータのフォルダに置く（入れ直しで消えないように）

**フォーム連携: Apps Script のウェブアプリ**
- `doPost`（POST で呼ばれたときに動く関数）で秘密キーを確かめてから、フォームの回答を JSON で返す（公式: https://developers.google.com/apps-script/guides/web ）
- 応答は script.googleusercontent.com へ転送されるので、ツールの HTTP の部品は転送をたどる設定にする（公式: https://developers.google.com/apps-script/guides/content ）
- 細かい決まりは仕様の3章

**ほかのサイトからの攻撃を防ぐ（ログインがないため）**
- ツールの中の Web サーバーは 127.0.0.1（そのPCの中からだけ届く住所。「ループバック」と呼ぶ）でだけ待ち受ける。ほかのPCからつながらないようにするため
- `Host` ヘッダー（どのアドレスあてに送ったか）が `127.0.0.1:<ポート>` か `localhost:<ポート>` でない要求は断る。DNSリバインディング（ほかのサイトが、自分の名前でこのPCのツールにつないでデータを読む攻撃）を防ぐため
- データを変える要求（POST・PUT・PATCH・DELETE）は、`Origin` ヘッダー（どのサイトの画面から送ったか）がツール自身のときだけ受け付ける。CSRF（ほかのサイトが、裏で削除などの命令を送る攻撃）を防ぐため
- 送る内容は JSON だけを受け付け、ほかのサイトからの呼び出しを許す CORS の設定はしない
- すべての応答に `X-Frame-Options: DENY` と `Content-Security-Policy: frame-ancestors 'none'` を付け、ツールの画面をほかのページの中（iframe）に表示させない。ほかのサイトが画面を透明にして重ね、ボタンを押させる攻撃（クリックジャッキング）を防ぐため（公式: https://developer.mozilla.org/docs/Web/HTTP/Reference/Headers/X-Frame-Options ）

## 2. データモデル（SQLite）

データは1つのファイル（`fleet-analysis.db`）に入れる。表の形は `backend/infra/src/main/resources/db/migration/` の SQL ファイルで決める（いまは `V1__create_tables.sql`）。表の形を変えるときは、今のファイルは直さずに `V2__xxx.sql` を足す（配信者さんのPCには、もう V1 で作った表があるため）。

| 表 | 1行の中身 | 主な列 |
|---|---|---|
| `applications`（応募） | 応募1件 | 応募ID、フォームの回答ID（UNIQUE。同じ回答を2件登録しない）、XのID（正規化済み。索引あり）、提督名、匿名希望、シミュレータURL、フォームの版、回答（JSON）、受付日時、印（JSON）、ステータス、見送りの理由、配信日、メモ、分析メモ、配信アーカイブURL、並び順キー、抽選で当選したか、更新日時、ステータス変更日時、版 |
| `application_history`（変更履歴） | ステータスの変更やXのIDの修正1回 | 書き込んだ順の番号（自動）、履歴ID、応募ID（索引あり）、日時、種類、変更前、変更後、補足（見送りの理由、どの操作で変わったか）。応募と同じトランザクションで書く |
| `lotteries`（抽選記録） | 抽選1回 | 抽選ID、方式（まとめ/配信中）、実行日時、乱数の種、対象者ごとの当たりやすさと結果（JSON） |
| `settings`（設定） | 設定の種類ごとに1行 | 種類（いまは `lottery` だけ）、設定内容（JSON）、版 |

- SQLite には日時の型がないので、日時は文字で入れる。秒の端数を必ず9桁にそろえ（例: `2026-10-01T10:00:00.000000000Z`）、文字の順に並べると日時の順になるようにする
- 回答・印・抽選の対象者のように、形が版ごとに変わったり、まとめて読み書きしたりするものは JSON の文字で1つの列に入れる
- 後の段階で、配信の操作履歴（「元に戻す」に使う。段階7）、抽選の取り消し（段階8）、条件ルール・選択肢の設定（段階9）などを、`V2__` 以降の SQL ファイルで足す

応募者ごとの「落選回数」や「最終当選日時」は保存しない。同じ人の応募と抽選の結果を集めて毎回数え直す（1人の応募は多くても数十件なので速さは問題にならない）。保存しておくと、抽選の取り消しやXのIDの修正のたびに直す必要があり、ずれの原因になるため。

並び順キー: 受付時は受付日時から作り、手動で並べ替えたら前後のキーの間の値を入れる（全件の振り直しが不要。動かした1件だけ保存するので、動かしていない応募の版は変わらない）。間に入る数がなくなったときだけ、そのグループを振り直す。ほかのステータスから移ってきたときは最後尾（中断のときは先頭）のキーを入れる。

版（同時変更の検知）: 応募は版の番号を持ち、保存のたびに1増える。保存は `UPDATE ... WHERE id = ? AND version = ?`（読み込んだときと版が同じ行だけを書き換える）で行い、書き換えた行が0なら（ほかの画面で先に保存していれば）409にする。画面は読み込んだときの版を送る。使う人は配信者さん1人だが、管理画面を2つのタブで開いたときや、取り込み（段階5）と画面の操作が重なったときに、変更を消さないため。

まとめての保存: 1回の操作で変わる応募（本人、印が変わった同じ人の応募、まとめて変えた応募）は1つのトランザクションで保存する（全部か何もしないか）。トランザクションは、始めた時点で書き込みの順番待ちに入る形（`BEGIN IMMEDIATE`。公式: https://www.sqlite.org/lang_transaction.html ）にしているので、確かめてから書くまでの間にほかの書き込みが割り込まない。まとめてのステータス変更は1回25件まで（以前の保存先 DynamoDB の制限から決めた数。SQLite にはこの制限はない）。抽選は1件ずつ保存する（DynamoDB の制限で決めた形。SQLite では1回にまとめられる）。抽選記録を先に保存し、途中でほかの変更とぶつかった応募は読み直してやり直す（段階8の取り消しと合わせて見直す）。

保存先の切り替え: 設定 `app.storage` が `sqlite`（ふだんの形）なら SQLite、`memory` ならメモリ（止めると消える。テストと、サンプルデータで画面を試すとき用）。SQLite のファイルは設定 `app.data-dir` のフォルダに置く。既定は Windows の利用者ごとのデータのフォルダ（`%LOCALAPPDATA%\KancolleFleetAnalysis`）。置き場所とバックアップは段階6で決め直す。

規模の想定: 応募は数百〜数千件。一覧は全件を1回で読んでも問題ない。

## 3. API（概要）

詳細は [openapi.yaml](../api/openapi.yaml)。

ログインはないので、どのAPIも「誰が呼んだか」を確かめない。代わりに、すべての要求の Host と Origin を確かめる（1章「ほかのサイトからの攻撃を防ぐ」、`backend/app` の `LocalAccessFilter`）。

| メソッド | パス | 役割 |
|---|---|---|
| GET | /applications | 一覧（絞り込み、次に分析する順） |
| GET | /applications/{id} | 詳細 |
| PATCH | /applications/{id} | ステータス・配信日・メモ・見送りの理由・分析メモ・アーカイブURL・XのIDの変更（版が古ければ409） |
| POST | /applications/bulk-status | 複数の応募のステータスをまとめて変更。1件でも変えられなければ全部を変えない（全部か何もしないか） |
| POST | /applications/{id}/keep | 重複の解消（この応募を残し、同じ人のほかの未完了を見送り） |
| PUT | /applications/{id}/position | 並べ替え |
| GET | /applications/{id}/history | 変更履歴（ステータス・XのIDを、いつ・何から何へ） |
| GET | /applicants/{xId}/applications | 同じ応募者の履歴 |
| DELETE | /applicants/{xId} | 削除依頼への対応 |
| GET | /stream/current | 配信用画面の表示内容（いま分析中の1人） |
| POST | /stream/next | 次の人へ（画面に出ていた分析中の応募IDを送り、違えば409にするのは段階7） |
| POST | /stream/pause | 中断（分析中の人を分析予定の先頭へ）。画面に出ていた応募IDを送り、違えば409（まだない。段階7） |
| POST | /stream/undo | 直前の「次の人へ」「中断」を元に戻す。操作履歴のIDを送り、最新でなければ409（まだない。段階7） |
| POST | /lotteries | 抽選の実行（まとめ／配信中／配信中の締め） |
| GET | /lotteries | 抽選記録 |
| POST | /lotteries/{id}/cancel | 一番新しい抽選の取り消し（まだない。段階8） |
| GET/PUT | /settings/{kind} | 設定の取得・変更 |
| POST | /imports/csv | 旧スプレッドシートの取り込み（今は501を返す。段階9） |

段階4でなくしたAPI: 応募受付（`POST /intake/applications`。段階5でツールが取りに行く形に変える）、ログインしている人（`GET /me`）、仮ログイン（`/dev/...`）、関係者への配信の操作の許可（`/stream/operators`）、ユーザー管理（`/users`）。変更履歴と抽選記録の「実行した人」もなくした（使う人が配信者さん1人なので）。

v1.2 で増えるAPI（段階4〜6で、先に openapi.yaml に書く）:
- フォームの取り込み: 最後に取り込んだ日時と結果を見る、「今すぐ取り込む」
- フォームとのつなぎ方の設定: ウェブアプリのURLと秘密キー
- バックアップ: 写しの一覧、今すぐ写しを作る、写しから戻す（ファイルを選ぶことも）、保存先の設定

## 4. 業務ロジックの要点

- 重複・再応募の判定は受付時に行い、印として保存する。同じ人のほかの応募のステータスやXのIDが変わったときにも付け直す（判定ルールを変えたら全件の再判定を実行できる）
- 印は「自分より前に受け付けた同じ人の応募」だけを見て決める。重複 = 自分がまだ終わっていなくて、前にまだ終わっていない応募がある。再応募 = 前に終わった応募（分析済み・見送り・落選）がある。取り込みやCSV取り込みで古い回答があとから入っても、受付日時（回答した日時）の順で決まる
- 抽選の重み: `weight = 1 + 落選回数 × 補正の強さ`（補正オフなら常に1）。重み付き非復元抽出
- 乱数の種は抽選ごとに生成して記録する。同じ種と対象者なら同じ結果が再現できる
- ステータス遷移は表で定義し、許されない遷移はエラーにする。「落選」へは抽選からだけ変えられる。抽選・「次の人へ」・重複の解消など仕組みが行う変更は、手で変えるときの表とは別の入口（`changeStatusBySystem`）を通す
- 同時に変更されたときは、応募の版を比べて後から来た変更を409にする（v1.1 は DynamoDB の条件付き書き込み。v1.2 は SQLite の `UPDATE ... WHERE version = ?`）

仕様 v1.1（運用目線の見直し）で、試作版と違うところ（各段階で直す）:
- 試作版の配信用画面にはボタンがあるが、v1.1では表示専用にして操作パネルを分ける（段階7）
- 試作版は比較の相手が「前回の応募」だが、v1.1では「前回分析した応募」（段階2で対応済み）
- 試作版は重複の印が受付時のまま変わらないが、v1.1では同じ人のほかの応募が変わるたびに付け直す（段階2で対応済み）
- 試作版は手で「落選」にできるが、v1.1では抽選でだけ付く（段階2で対応済み）
- 試作版の「次の人へ」は分析予定・未着手の選び方（印の扱い、抽選オンのとき未着手を選ばない）はv1.1と同じ。同時の操作の検知と「元に戻す」はまだない（段階7）
