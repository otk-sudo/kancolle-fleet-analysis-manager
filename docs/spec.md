# 艦隊分析 応募者管理ツール 仕様書

版: v1.2（2026-10-03）。ツールを、配信者さんのPCだけで動かす形に変えた。変更点は付録Cにある。v1.1の見直しは付録B

## 1. 概要

### 1.1 目的
配信者さんが行う「艦隊分析」への応募が殺到しており、応募者の管理が大変になっている。
その応募管理をサポートするツールを作る。配信者さんのPCにインストールして、そのPCのブラウザで使う（v1.2で決定。付録C）。艦隊の分析・計算そのものは対象外。

### 1.2 解決する課題（優先順）
1. 進捗管理: 誰が分析済みで、次は誰か
2. 重複応募・条件外応募のチェック
3. 応募内容の読みやすい整理（フォーム回答を一覧・詳細・配信用に見やすく表示）

あわせて実現すること:
- 同じ応募者の過去の応募と比較できるよう、履歴を残す
- 応募が多すぎるときの抽選

### 1.3 対象外（現時点）
- 応募者への連絡・結果告知
- 制空権シミュレータURLの中身の読み取り（URLを保存してリンクで開くのみ）

### 1.4 開発の位置づけ
開発者（OTさん）の仕事での学習を兼ねる。Java＋OpenAPI＋Gradleを使い、保守性・拡張性を重視する。v1.2でAWSは使わないことにした（付録C）。

**作るところから公開（配信者さんに使ってもらう）まで、すべて無料の範囲で行う**（2026-10-03 OTさんが決定）。お金がかかるサービスや、使いすぎるとお金がかかる設定は使わない。

## 2. 利用者と権限

- ツールを使うのは、ツールを入れたPCを使う配信者さんだけ。応募の管理、抽選、配信の操作、設定、削除依頼への対応をすべて行う
- ログインはない。ツールはそのPCの中からだけ開ける（同じネットワークのほかのPCやインターネットからはつながらない）ようにし、PCのログインで守る
- ただし、同じPCのブラウザで開いたほかのWebサイトが、裏でツールに命令を送ろうとすることがある（「CSRF」や「DNSリバインディング」と呼ばれる攻撃）。ログインがないので、ツールの側で次のように防ぐ（詳しくは設計メモ）
  - ツールのアドレス（127.0.0.1 と localhost）あての要求だけを受け付ける。別の名前で届いた要求は断る（DNSリバインディングで、ほかのサイトがデータを読むのを防ぐため）
  - データを変える要求は、ツール自身の画面から送られたものだけを受け付ける（ほかのサイトから送られた削除などの命令を断るため）
- 開発者（OTさん）はツールを使わない。直したツールを配り、困ったときに手伝う
- v1.1にあった「運営」「関係者」の役割、関係者への配信の操作の許可、二段階認証は、v1.2でなくした（付録C）
- 応募者本人はツールを使わない（Googleフォームから応募するだけ）

## 3. 全体の流れ

```
応募者 ──回答──▶ Googleフォーム ──▶ スプレッドシート（控え）
                       │
                       └─ Apps Script（ウェブアプリとして公開。回答を返す窓口）
                                 ▲
                                 │ 回答を取りに行く（秘密キー付き）
配信者さんのPC: ツール（起動中）──┘
  ├─ 管理画面・配信の操作パネル（ブラウザ）
  ├─ 配信用画面（配信ソフトのブラウザソースで映す）
  └─ データ（PCの中のファイル）＋自動のバックアップ
```

- 配信者さんのPCはいつも起動しているとは限らず、外から届くURLもないので、フォームからツールへ送る（v1.1）のではなく、ツールがフォームの回答を取りに行く
- Apps Script はフォームに結びついたスクリプトにし、「ウェブアプリ」（URLで呼べる窓口）として公開する。ツールから呼ばれたら、フォームの回答を返す（公式: https://developers.google.com/apps-script/guides/web ）。ツールの側にはGoogleのアカウントの情報を持たせない
  - 公開の設定は「次のユーザーとして実行: 自分」「アクセスできるユーザー: 全員」にする。ツールはGoogleにログインせずに呼ぶので、こうしないと呼べないため
  - ウェブアプリのURLを知っていれば誰でも呼べてしまうので、フォーム用の秘密キーを一緒に送らないと回答を返さないようにする
  - 秘密キーはURLに入れず、POST（送る内容の本文）に入れる。URLは記録や履歴に残りやすいため
  - 秘密キーは Apps Script のコードに書かず、スクリプト プロパティ（スクリプトごとの設定の保存場所）に入れる
  - 秘密キーが漏れたときに備え、作り直して両方に設定し直す手順を用意する
  - Apps Script の応答は、一度だけ使える別のURL（script.googleusercontent.com）へ転送される。ツールはその転送をたどる（公式: https://developers.google.com/apps-script/guides/content ）
- ツールは、起動したときと、起動している間は数分ごとに、前回より後の回答を取りに行く。管理画面の「今すぐ取り込む」でも取りに行ける
  - Apps Script は、日時を渡して回答を取り出せる（`getResponses`。公式: https://developers.google.com/apps-script/reference/forms/form ）。ツールは「最後に取り込んだ回答の日時」を覚えておき、その日時「以後」の回答をもらう。同じ日時の回答を取りこぼさないよう「以後」にし、同じ回答は回答IDで見分けて二重に登録しない
  - 1回の実行は6分までなので（公式の上限のページ）、一度に返す件数に上限を付け、続きがあればツールが続けて取りに行く。初めての取り込みでは数千件になることがある
  - 「最後に取り込んだ回答の日時」は、取り込んだ回答を保存し終えてから進める（途中で失敗しても取りこぼさないため）
  - フォームの「送信後に回答を編集」はオフにしておく。編集された回答は同じ回答IDで届くので、ツールには反映されないため（フォームの設定: 公式 `setAllowResponseEdits`、同じページ）
- ツールを起動していない間に届いた回答は、次に起動したときにまとめて取り込む（v1.1の「未連携」と「再送」はなくなる）
- 取り込みに失敗したとき（ネットにつながらない、秘密キーが違うなど）は、管理画面に理由を出す
- Apps Script は無料で使える。上限は、1回の実行が6分まで、同時に動かせるのは1人あたり30まで、など（Googleの個人アカウントの場合。公式: https://developers.google.com/apps-script/guides/services/quotas ）。数分ごとの取り込みなら上限に届かない見込み（推測）
- 応募の受付開始・締切はGoogleフォームの「回答を受け付ける」（Accepting responses）の切り替えや締切日の設定で行い、ツール側では管理しない（公式: https://support.google.com/docs/answer/139706 ）
- スプレッドシートは控えとして残すが、普段の運用では開かない（配信に映さないため）

## 4. 応募フォーム

### 4.1 フォーム冒頭の注意書き（個人情報の取り扱い）
- 利用目的: 応募管理、重複確認、過去の分析との比較
- 保管期間: 原則無期限（過去の分析と比較するため）。削除依頼があれば削除する
- 閲覧者: 配信者さん（ツールは配信者さんのPCの中だけで動く）
- 配信での公開: 分析するときは、回答（XのIDと課金額を除く）と提督名を配信に映す。配信のアーカイブにも残る。名前を出したくない人は「匿名希望」を選べる
- バックアップ: 削除後も、バックアップの保持期間（30日）が過ぎるまではバックアップの中に残る
- 削除依頼の連絡先: 配信者さん

※ 一般論としての方針で、法律の専門家による確認ではない。

## 5. 応募の管理

### 5.1 ステータス
| ステータス | 意味 | 次に分析する人の候補 |
|---|---|---|
| 未着手 | 受け付けたばかり | ○ |
| 分析予定 | 分析することが決まった（抽選の当選を含む）。配信日は任意で設定 | ○ |
| 分析中 | 配信で分析している | − |
| 分析済み | 分析が終わった | − |
| 見送り | 重複・条件外・取り下げなどで分析しない（理由を選ぶ。5.6） | − |
| 落選 | 抽選で外れた。抽選でだけ付く（手で「落選」にはしない） | − |

- 上の6つは仕組みが前提にしている「固定のステータス」で、名前の表示は変えられるが消せない。設定で追加したステータスは「終わったもの」として扱い、次に分析する人や抽選の候補にはならない
- ステータス変更は「いつ・何から何へ」を履歴に残す
- 2つのタブ（画面）で同時に同じ応募を変えたときは、後から保存した画面に「ほかの画面で先に変更しました」と知らせ、上書きしない

ステータスを手で変えられる組み合わせ（○）。「−」は手では変えられない:

| 今 ＼ 変更後 | 未着手 | 分析予定 | 分析中 | 分析済み | 見送り | 落選 |
|---|---|---|---|---|---|---|
| 未着手 | | ○ | ○ | − | ○ | − |
| 分析予定 | ○ | | ○ | − | ○ | − |
| 分析中 | ○ | ○ | | ○ | − | − |
| 分析済み | − | − | ○ | | − | − |
| 見送り | ○ | − | − | − | | − |
| 落選 | − | − | − | − | − | |

- 「落選」は抽選の結果でだけ付き、抽選の取り消し（6.4）でだけ外れる。手で付けたり外したりできると、落選補正（6.3）の回数が実際の抽選とずれるため
- 仕組みが行う変更: 抽選（未着手→分析予定／分析中／落選）、抽選の取り消し（その逆）、次の人へ（分析中→分析済み、分析予定・未着手→分析中）、中断（分析中→分析予定）、元に戻す（その逆）、重複の解消（未着手・分析予定→見送り）
- 「分析済み→分析中」は、間違えて分析済みにしたときに戻すため
- まとめてのステータス変更（5.6）も、この表の範囲でだけ行える

### 5.2 重複・再応募の判定
同じXのID（正規化後）で判定する。
- 重複: 同じIDで「未着手・分析予定・分析中」の応募がすでにある → 新しい応募に「重複」の印をつける。自動で見送りにはせず、配信者が確認して判断する
- 再応募: 同じIDで「分析済み・見送り・落選」の応募が過去にある → 「再応募」の印をつけ、履歴と比較できるようにする
- 印は、関係する応募の状態が変わったら付け直す。例: 古い方を見送りにしたら、新しい方の「重複」は外れて「再応募」になる。印が残ったままだと、抽選や「次の人へ」で飛ばされ続けるため
- 重複の解消を一度で行える: 「この応募を残す」を押すと、同じ人のほかの「未着手・分析予定」の応募を「見送り（再送のため）」にする。応募者が内容を直して送り直した場合によく使う
  - 見送りにする中に「分析予定」（抽選の当選を含む）があれば、残す応募がそのステータス・並び順・当選の扱いを引き継ぐ。送り直しで当選が無駄にならないように
  - 「分析中」の応募があるときは使えない（先に分析を終えるか中断する）

### 5.3 条件外チェック
- 初期設定は「条件なし」
- 配信者が設定で条件を追加できる（例: 前回の分析済みから○ヶ月以内は条件外）
- 条件外に当たった応募には印と理由を表示する。自動で見送りにはしない
- 条件は差し替え可能なルールとして実装し、種類を後から増やせるようにする

### 5.4 次に分析する人の並び順
- 対象は「分析予定」と「未着手」。分析予定を先に、その中はそれぞれ受付順
- 配信者は一覧で手動で並べ替えられる。手動で動かした順番は保持する
- 並べ替えは同じステータスの中でだけ行う。並べ替えでステータスは変わらない（分析予定にしたいときはステータスを変える）
- 配信日は表示とメモのためのもので、並び順には影響しない
- ほかのステータスから「分析予定」「未着手」に移った応募は、そのグループの最後尾に入る。ただし配信の中断（7.3）で「分析予定」に戻した応募は先頭に入れ、次の配信で続きから始められるようにする

### 5.5 過去応募との比較
- 比較の相手は「前回分析した応募」（同じXのIDで「分析済み」のうち一番新しいもの）。見送り・落選の応募は分析していないので、比較の相手にしない
- 同じXのIDの応募を時系列で並べ、選択式の項目（実働期間、課金額、プレイ時間、戦果、縛り、目的）は変化がわかるように表示する
- 自由記述（目標、相談内容）は並べて表示する
- 分析済みにするときに「分析メモ」（配信者が残す要点）と「配信アーカイブのURL」（時刻付きのリンクも可）を残せる。次に同じ人を分析するとき、前回の内容をすぐ振り返れるようにするため（管理画面だけに表示。配信用画面には前回の分析日だけを出す）

### 5.6 見送りの理由と、あとからの修正
- 見送りにするときは理由を選ぶ: 重複（再送のため）、条件外、本人の取り下げ、その他（メモ）
- 応募者からの取り下げの連絡は配信者が受け、「見送り（本人の取り下げ）」にする
- 応募者がXのIDを打ち間違えた場合、配信者がXのIDを直せる。直すと重複・再応募の印と履歴の紐づけを付け直し、変更前のIDを操作履歴に残す
- 複数の応募をまとめて選んでステータスを変えられる（例: 条件外をまとめて見送り）

## 6. 抽選

### 6.1 基本
- 設定で「抽選を使う／使わない」を切り替える。使わない場合は5.4の並び順のみ
- 抽選の対象は「未着手」の応募。重複・条件外の印がついたものは初期状態で除外し、配信者が対象に戻すこともできる
- 当選した応募は「分析予定」、管理画面のまとめ抽選で外れた応募は「落選」になる
- 同じ人（同じXのID）の応募が対象に複数あっても、1人1回分として抽選する。抽選の確認画面で「重複が解消されていない人」を知らせ、先に解消（5.2）するよう促す。解消しないまま抽選した場合は、受付が一番早い応募をその人の代表にし、結果は代表にだけ付ける（ほかの応募は未着手のまま「重複」の印が残る）

### 6.2 抽選のしかた（両方に対応）
- まとめ抽選: 受付締切後に管理画面で当選人数を指定して一度に抽選する
- 配信中の抽選: 配信の操作パネル（7.3）で1人ずつ抽選し、結果を配信用画面に表示する。当選した人はそのまま「分析中」にできる。分析中の人がいるときは、先に分析済みか中断にしてから抽選する。配信中の抽選では外れた人を落選にせず、未着手のまま残す。抽選1回（1人を選ぶ）ごとに1件の抽選記録を残す
- 配信中の抽選の締め: 配信の最後に、残った「未着手」の対象者を落選にする操作。当選者0人の抽選として記録を残し、対象者全員を「外れ」として記録する。こうすると「落選は抽選でだけ付く」決まり（5.1）と、記録・取り消し・落選回数の数え方がそろう

### 6.3 落選補正
- 落選した人は次回再応募が必要
- 再応募したとき、同じXのIDの落選回数が多いほど当たりやすくする（初期値: 当たりやすさ = 1 + 落選回数）
- 落選回数は「最後に当選してから、外れになった抽選の数」で数える（抽選1回につき1回。配信中の抽選で外れて未着手のまま残った分は数えず、締めで落選になったときに1回と数える）。当選したらリセット
- 落選回数は保存せず、応募と抽選記録から毎回数え直す。抽選の取り消しやXのIDの修正をしても、数がずれないようにするため
- 設定で補正のオン・オフと強さを変えられる
- 初回応募者の優先はしない

### 6.4 記録
- 抽選ごとに「日時・対象者と各自の当たりやすさ・当選者・乱数の種」を記録し、後から公平性を確認できるようにする
- まとめ抽選は実行前に「対象人数・当選人数・外れた人が落選になること」を確認する画面を出す
- 一番新しい抽選記録（配信中の抽選なら直前の1回、締めも1回と数える）は取り消せる。当選人数の入れ間違いなどに備えるため。取り消すと、その抽選で変わったステータスを抽選の前に戻し、記録には「取り消し」と残す（記録自体は消さない）
- 抽選の後に、対象の応募が手や「次の人へ」などでさらに変更されていたら、取り消せないことを知らせる（例: 当選者がすでに分析中・分析済み）

## 7. 画面

### 7.1 管理画面（配信外で使う）
1. 応募一覧
   - 列: 受付日時、提督名、XのID、ステータス、重複／再応募／条件外の印、分析してほしい目的、戦果、縛りの有無
   - ステータス・目的・戦果・印で絞り込み、提督名・XのIDで検索
   - 複数を選んでまとめてステータス変更（5.6）
   - 「次に分析する人」の並びで表示し、ドラッグで並べ替え
2. 応募詳細
   - フォームの全回答、制空権シミュレータを開くリンク
   - ステータス変更、配信日、メモ、XのIDの修正（5.6）、重複の解消（5.2）
   - 分析済みにするときの分析メモ・配信アーカイブURL（5.5）
   - 過去応募との比較（5.5）
3. 抽選
   - 対象者の確認、当選人数の指定、実行（確認画面あり）、過去の抽選記録、一番新しい抽選の取り消し
4. 設定
   - 条件ルール、選択肢、ステータス、抽選設定
   - フォームとのつなぎ方（Apps Script のウェブアプリのURLと秘密キー）、バックアップの保存先
5. 取り込み
   - フォームの回答を最後に取り込んだ日時と結果、「今すぐ取り込む」、取り込みに失敗したときの理由（3章）
   - 旧スプレッドシートのCSV取り込み
6. バックアップ
   - バックアップの一覧と、選んだ時点に戻す操作（8.3）

### 7.2 配信用画面（配信に映す・表示専用）
- いま「分析中」の1人だけを表示する。XのID、ほかの応募者の情報、課金額は出さない
- 「匿名希望」の人は提督名の代わりに「匿名提督」などと表示する
- 表示項目: 提督名、着任時期、実働期間、プレイ時間、戦果、縛り、目標、相談内容、前回分析した応募との比較（5.5）、前回の分析日
- **ボタンや確認ダイアログを置かない表示専用の画面にする。** 操作は別の画面（7.3）で行う。配信ソフトで画面ごと映したときに、ボタンや「よろしいですか？」の確認、押し間違いが映らないようにするため
- 分析中の人が変わったら、数秒以内に自動で切り替わる（画面が数秒ごとに表示内容を読み直す方式。常時接続の仕組みは使わない）
- 配信中の抽選の演出（抽選中…→当選者の表示）もここに出す。外れた人の名前は出さない
- 配信ソフト（OBSのブラウザソースなど）には、同じPCの配信用画面のURL（例: http://127.0.0.1:<ポート>/stream ）をそのまま設定する。ログインがないので、閲覧専用URL（v1.1）は作らない

### 7.3 配信の操作パネル
配信中に、配信者さんがPCのブラウザで開く操作用の画面。配信に映らない別のタブやウィンドウで使う。v1.0の配信用画面にあったボタンは、すべてここへ移した。
- いま分析中の人と、次に分析する順の先頭数人（提督名と印）を表示する。XのIDと課金額は出さない（画面共有などで映ってしまう事故に備える）
- 「配信の操作」は次の5つ
  1. 次の人へ: 分析中の人を「分析済み」にし、次に分析する順（5.4）の先頭の人を「分析中」にする。分析中の人がいないとき（配信の始め）は、先頭の人を「分析中」にするだけ。押すときに確認を出す
     - 「分析予定」の人は、配信者さんが分析すると決めた人なので、印があってもそのまま選ぶ
     - 「未着手」の人は、重複・条件外の印があれば飛ばす
     - 抽選を使う設定のときは「未着手」の人を選ばない（未着手の人は抽選で選ぶ）。分析予定の人がいなければ、分析済みにするだけで、パネルには「次の人は配信中の抽選で選んでください」と出す
  2. 中断: 配信が終わるなどで分析を途中でやめるとき、分析中の人を「分析予定」の先頭に戻す
  3. 元に戻す: 直前の「次の人へ」か「中断」を1回分だけ取り消す（押し間違いに備える）。その後に対象の応募がほかの操作で変わっていたら取り消せない
  4. 配信中の抽選（6.2、抽選を使う設定のとき）
  5. 配信中の抽選の締め（6.2、抽選を使う設定のとき）
- 操作パネルを2つのタブで開いていても二重に進まないよう、操作するときは「画面に出ていた分析中の人」を一緒に送る。その間にほかのタブで進めていたら、操作せずに「ほかの画面で先に操作しました」と知らせる
- シミュレータを開くボタン（配信者さんが艦隊を確認するため）
- PCで使う前提にする。スマホ向けの画面は作らない（配信中の操作はPCの別タブで足りるため。必要になったら、そのときに追加を検討する）

## 8. データの扱い

### 8.1 個人情報
- 集めるのは4.2の項目だけ。メールアドレスや本名は取らない
- スプレッドシートとフォームは、配信者さんだけが見られるようにする（ほかの人と共有しない）。開発者が手伝うときも、応募の中身は見ない
- 削除依頼は、本人のXアカウントからのDMなど本人だと確かめられる方法でだけ受け付ける。他人になりすました削除依頼で、別の人のデータを消してしまわないため
- 削除するもの: ツールの応募データ、Googleフォームに残る回答、スプレッドシートの控え。フォームとスプレッドシートは別々のファイルなので、両方から消す必要がある（推測。フォームとスプレッドシートが別のファイルであることは公式: https://support.google.com/docs/answer/2917686 ）
- フォームの回答は、Apps Script の `deleteResponse`（回答IDを指定して消す）で消せる（公式: https://developers.google.com/apps-script/reference/forms/form ）。ツールの削除の画面から、Apps Script に頼んでフォームの回答も消すようにし、手で消す手間を減らす（スプレッドシートの控えは手で消す）
- ツールの中では、応募と、そのXのIDを含む操作履歴・配信の操作履歴を消す。抽選記録に残る応募IDは「削除済み」に置き換える（抽選の公平性の確認に必要な当たりやすさと結果は残す）
- 削除の画面では、消える応募の件数と内容を確認してから実行する。実行後に、フォームの回答とスプレッドシートの控えからも消す手順を表示する
- 削除すると落選回数（6.3）も数えられなくなるため、その人が再応募したときは初めての応募として扱われる。削除の画面でそのことを伝える
- 操作履歴には「いつ削除したか」だけを残し、削除された人の情報は残さない
- バックアップ（8.3）には保持期間のあいだ残る。フォームの注意書き（4.1）に書いておく。OneDrive などに置いたバックアップは、そのサービスのごみ箱にしばらく残ることがある（推測）
- 削除した人を、バックアップから戻したときに生き返らせないよう、「削除した記録」（XのIDを元に戻せない形に変えた値と、削除した日）をデータとは別のファイルに残す。バックアップから戻したあと、この記録にある人のデータを自動でもう一度消す

### 8.2 既存応募の取り込み
- 今のスプレッドシートにある応募もツールに取り込む
- 旧スプレッドシートの列構成は未定。「列と新項目の対応表」を渡せる汎用のCSV取り込み機能として作り、列構成が決まってから対応表を用意する
- 対応する項目がないものは空欄にし、「旧フォームの版」として記録する
- 旧フォームの応募者は新しい取り扱い（無期限保管・比較）に同意していないため、Xなどで取り扱い変更を告知しておくのが望ましい

### 8.3 バックアップ
- データはPCの中の1つのファイルに保存する。PCの故障や誤操作でデータを失わないよう、ツールが自動でバックアップを作る
  - ツールを起動したときと、起動している間は1日1回、データのファイルの写しを作る
  - 写しは30日分を残し、それより古いものは消す
  - 保存先は設定で変えられる。PCが壊れても残るよう、外付けディスクや、OneDrive などクラウドと同期しているフォルダを選ぶことを勧める（画面で案内する）
  - 写しは「30日より古いものを消す。ただし、新しい5件はいつも残す」。PCを長く使わなかったときに、写しが1つだけにならないようにするため
- バックアップの画面で、写しを選んでその時点に戻せる。戻す前に、今の状態の写しを作る。保存先にない写し（別のPCから持ってきたものなど）も、ファイルを選んで戻せる
- 戻したあと:
  - 削除した記録（8.1）にある人のデータを、もう一度消す
  - フォームの取り込みの位置も写しの時点に戻るので、それより後の回答をもう一度取り込む（同じ回答は回答IDで見分けるので、二重にはならない）
- 写しは、使用中のデータベースからでも安全に作れる方法を使う（設計メモ）

### 8.4 新しいPCへの引っ越し・入れ直し
- データのファイルとバックアップは、インストール先とは別のフォルダ（Windows の利用者ごとのデータのフォルダ）に置く。ツールを入れ直したり新しい版に上げたりしても、データが消えないようにするため
- 新しいPCに移るときは、新しいPCにツールを入れ、バックアップの画面で古いPCの写しを選んで戻す
- フォームとのつなぎ方（ウェブアプリのURLと秘密キー）もデータの中に保存するので、戻せば一緒に移る

### 9.1 起動と終了
- ツールを起動すると、黒い画面（コンソール）は出さずに、ブラウザで管理画面を自動で開く。タスクトレイ（画面の右下）にアイコンを出し、そこから「管理画面を開く」「終了」を選べる
- 使う番号（ポート）は決まった番号にする。配信ソフトに設定する配信用画面のURLに入るため。設定で変えられる
- その番号をほかのソフトが使っていて起動できないとき、またはツールがすでに起動しているときは、そのことを画面（小さな窓）で知らせる。ツールが2つ同時に動いて、同じデータのファイルを壊さないようにするため
- Windows の起動と一緒にツールを起動するかは、設定で選べる（初期値: しない）。配信の前に起動しておく必要がある

## 10. 保守性・拡張性の方針
- 選択肢・ステータス・条件ルール・抽選設定はコードに直書きせず設定データとして持つ。選択肢を変えても過去の回答はそのまま残す
- 応募には「フォームの版」を記録し、質問項目が増減しても古い応募を読める
- OpenAPI定義を唯一の正とし、バックエンドと画面の型はそこから生成する
- バックエンドは層を分ける（API／業務ロジック／データアクセス）。データベースへのアクセスは差し替え可能にする（あとでサーバーに置くことになっても、業務ロジックはそのまま使えるように）
- 重複判定・条件外チェック・抽選の重みづけは差し替え可能なルールとして実装し、単体テストを書く
- 操作の履歴（ステータス変更、抽選、設定変更、削除）を残す

## 付録A: 制空権シミュレータURLの読み取り（将来の拡張用の調査結果、2026-10-02）
制空権シミュレータ（noro6/kc-web）のソースコードで確認した内容。現時点では実装しない。
- 「共有URLを生成」で出るのは短縮URL。転送先は `https://noro6.github.io/kc-web?data=...` の長いURL
- `data` は編成データ（JSON）を標準の lz-string（compressToEncodedURIComponent）で圧縮したもの
- 中身は艦・装備のIDと改修値・熟練度・レベルなどで、名前は入っていない（名前への変換にはマスタデータが必要）
- 内部形式は公式な仕様ではないため、シミュレータ側の更新で変わる可能性がある
