# 艦隊分析 応募者管理ツール 仕様書

版: v1.1（2026-10-02 運用目線で見直し。変更点は付録B）

## 1. 概要

### 1.1 目的
配信者さんが行う「艦隊分析」への応募が殺到しており、応募者の管理が大変になっている。
その応募管理をサポートするWebツールを作る。艦隊の分析・計算そのものは対象外。

### 1.2 解決する課題（優先順）
1. 進捗管理: 誰が分析済みで、次は誰か
2. 重複応募・条件外応募のチェック
3. 応募内容の読みやすい整理（フォーム回答を一覧・詳細・配信用に見やすく表示）

あわせて実現すること:
- 同じ応募者の過去の応募と比較できるよう、履歴を残す
- 応募が多すぎるときの抽選

### 1.3 対象外（現時点）
- 応募者への連絡・結果告知
- 制空権シミュレータURLの中身の読み取り（URLを保存してリンクで開くのみ）

### 1.4 開発の位置づけ
開発者（OTさん）の仕事での学習を兼ねる。Java＋OpenAPI＋Gradle＋AWSを使い、保守性・拡張性を重視する。

## 2. 利用者と権限

| 役割 | 想定する人 | できること |
|---|---|---|
| 運営 | 開発者などの管理者 | 全権限。すべての操作、設定変更、全ユーザー管理、削除依頼への対応 |
| 配信者 | 分析を行う配信者さん | 応募の閲覧・ステータス変更・並べ替え・メモ、抽選、配信用画面、設定変更（条件ルール・選択肢・抽選設定）、関係者アカウントの追加・削除 |
| 関係者 | 配信者さんの手伝いをする人 | 一覧・詳細の閲覧と配信用画面の表示。配信者が許可すれば配信の操作（7.3）も |

- 配信者は運営アカウントを操作できない
- 関係者に配信の操作（次の人へ・中断・配信中の抽選）を許可するかは、配信者が関係者ごとに設定する（初期値: 許可しない）。配信中の進行を手伝ってもらうため
- 配信者・運営のアカウントは二段階認証（MFA）を使う。応募者の個人情報を扱い、削除もできる権限のため
- 役割はCognitoのグループで管理し、APIの各操作で権限を確認する
- 応募者本人はツールにログインしない（Googleフォームから応募するだけ）

## 3. 全体の流れ

```
応募者 ──回答──▶ Googleフォーム ──▶ スプレッドシート（控え）
                       │
                       └─ Apps Script（送信時トリガー）──▶ 応募受付API ──▶ DynamoDB
                                                                   │
配信者・関係者・運営 ──ログイン──▶ 管理画面 / 配信用画面（React）──▶ 管理API
```

- Apps Scriptはフォーム送信時に回答をAPIへ送るだけの数行にとどめる
- 受付APIはフォーム専用の秘密キーで認証する（ログイン不要の代わりに、キーを知らない送信は拒否）
- 送信に失敗した回答は、スプレッドシートに「未連携」の印を残し、管理画面から再取り込みできる
- フォーム用の秘密キーが漏れたときに備え、運営が再発行でき、Apps Script側の差し替え手順を用意しておく
- 応募の受付開始・締切はGoogleフォームの「回答を受け付ける」の切り替えで行う（ツール側では管理しない）
- スプレッドシートは控えとして残すが、普段の運用では開かない（配信に映さないため）

## 4. 応募フォーム

### 4.1 フォーム冒頭の注意書き（個人情報の取り扱い）
- 利用目的: 応募管理、重複確認、過去の分析との比較
- 保管期間: 原則無期限（過去の分析と比較するため）。削除依頼があれば削除する
- 閲覧者: 配信者さんとその関係者、運営
- 削除依頼の連絡先: 配信者さんまたは運営

※ 一般論としての方針で、法律の専門家による確認ではない。

## 5. 応募の管理

### 5.1 ステータス
| ステータス | 意味 | 次に分析する人の候補 |
|---|---|---|
| 未着手 | 受け付けたばかり | ○ |
| 分析予定 | 分析することが決まった（抽選の当選を含む）。配信日は任意で設定 | ○ |
| 分析中 | 配信で分析している | − |
| 分析済み | 分析が終わった | − |
| 見送り | 重複・条件外・取り下げなどで分析しない（理由を選ぶ。5.6） | − |
| 落選 | 抽選で外れた。抽選でだけ付く（手で「落選」にはしない） | − |

- ステータスは設定データとして持ち、後から追加できる
- ステータス変更は「いつ・誰が・何から何へ」を履歴に残す
- 「落選」は抽選の結果でだけ付ける。手で付けられると落選補正（6.3）の回数が実際の抽選とずれるため。抽選の取り消し（6.4）では元に戻る
- 2人が同時に同じ応募を変えたときは、後から保存した人に「ほかの人が先に変更しました」と知らせ、上書きしない

### 5.2 重複・再応募の判定
同じXのID（正規化後）で判定する。
- 重複: 同じIDで「未着手・分析予定・分析中」の応募がすでにある → 新しい応募に「重複」の印をつける。自動で見送りにはせず、配信者・運営が確認して判断する
- 再応募: 同じIDで「分析済み・見送り・落選」の応募が過去にある → 「再応募」の印をつけ、履歴と比較できるようにする
- 印は、関係する応募の状態が変わったら付け直す。例: 古い方を見送りにしたら、新しい方の「重複」は外れて「再応募」になる。印が残ったままだと、抽選や「次の人へ」で飛ばされ続けるため
- 重複の解消を一度で行える: 「この応募を残す」を押すと、同じ人のほかの未完了の応募を「見送り（再送のため）」にする。応募者が内容を直して送り直した場合によく使う

### 5.3 条件外チェック
- 初期設定は「条件なし」
- 配信者・運営が設定で条件を追加できる（例: 前回の分析済みから○ヶ月以内は条件外）
- 条件外に当たった応募には印と理由を表示する。自動で見送りにはしない
- 条件は差し替え可能なルールとして実装し、種類を後から増やせるようにする

### 5.4 次に分析する人の並び順
- 対象は「分析予定」と「未着手」。分析予定を先に、その中はそれぞれ受付順
- 配信者・運営は一覧で手動で並べ替えられる。手動で動かした順番は保持する
- ほかのステータスから「分析予定」「未着手」に移った応募は、そのグループの最後尾に入る。ただし配信の中断（7.3）で「分析予定」に戻した応募は先頭に入れ、次の配信で続きから始められるようにする

### 5.5 過去応募との比較
- 比較の相手は「前回分析した応募」（同じXのIDで「分析済み」のうち一番新しいもの）。見送り・落選の応募は分析していないので、比較の相手にしない
- 同じXのIDの応募を時系列で並べ、選択式の項目（実働期間、課金額、プレイ時間、戦果、縛り、目的）は変化がわかるように表示する
- 自由記述（目標、相談内容）は並べて表示する
- 分析済みにするときに「分析メモ」（配信者が残す要点）と「配信アーカイブのURL」（時刻付きのリンクも可）を残せる。次に同じ人を分析するとき、前回の内容をすぐ振り返れるようにするため（管理画面だけに表示。配信用画面には前回の分析日だけを出す）

### 5.6 見送りの理由と、あとからの修正
- 見送りにするときは理由を選ぶ: 重複（再送のため）、条件外、本人の取り下げ、その他（メモ）
- 応募者からの取り下げの連絡は配信者・運営が受け、「見送り（本人の取り下げ）」にする
- 応募者がXのIDを打ち間違えた場合、配信者・運営がXのIDを直せる。直すと重複・再応募の印と履歴の紐づけを付け直し、変更前のIDを操作履歴に残す
- 複数の応募をまとめて選んでステータスを変えられる（例: 条件外をまとめて見送り）

## 6. 抽選

### 6.1 基本
- 設定で「抽選を使う／使わない」を切り替える。使わない場合は5.4の並び順のみ
- 抽選の対象は「未着手」の応募。重複・条件外の印がついたものは初期状態で除外し、配信者・運営が対象に戻すこともできる
- 当選した応募は「分析予定」、管理画面のまとめ抽選で外れた応募は「落選」になる
- 同じ人（同じXのID）の応募が対象に複数あっても、1人1回分として抽選する

### 6.2 抽選のしかた（両方に対応）
- まとめ抽選: 受付締切後に管理画面で当選人数を指定して一度に抽選する
- 配信中の抽選: 配信の操作パネル（7.3）で1人ずつ抽選し、結果を配信用画面に表示する。当選した人はそのまま「分析中」にできる。分析中の人がいるときは、先に分析済みか中断にしてから抽選する。配信中の抽選では外れた人を落選にせず、未着手のまま残す（配信の最後に、まとめ抽選と同じく残りを落選にするか選べる）

### 6.3 落選補正
- 落選した人は次回再応募が必要
- 再応募したとき、同じXのIDの落選回数が多いほど当たりやすくする（初期値: 当たりやすさ = 1 + 落選回数）
- 落選回数は「最後に当選してから」の回数で数える。当選したらリセット
- 設定で補正のオン・オフと強さを変えられる
- 初回応募者の優先はしない

### 6.4 記録
- 抽選ごとに「日時・実行者・対象者と各自の当たりやすさ・当選者・乱数の種」を記録し、後から公平性を確認できるようにする
- まとめ抽選は実行前に「対象人数・当選人数・外れた人が落選になること」を確認する画面を出す
- 直近の抽選は取り消せる（当選人数の入れ間違いなどに備える）。取り消すと、その抽選で変わったステータスを元に戻し、記録には「取り消し」と残す（記録自体は消さない）。取り消した後に手で変更した応募があれば、取り消せないことを知らせる

## 7. 画面

### 7.1 管理画面（配信外で使う）
1. 応募一覧
   - 列: 受付日時、提督名、XのID、ステータス、重複／再応募／条件外の印、分析してほしい目的、戦果、縛りの有無
   - ステータス・目的・戦果・印で絞り込み、提督名・XのIDで検索
   - 複数を選んでまとめてステータス変更（5.6）
   - 「次に分析する人」の並びで表示し、ドラッグで並べ替え
2. 応募詳細
   - フォームの全回答、制空権シミュレータを開くリンク
   - ステータス変更、配信日、メモ、XのIDの修正（5.6）、重複の解消（5.2）
   - 分析済みにするときの分析メモ・配信アーカイブURL（5.5）
   - 過去応募との比較（5.5）
3. 抽選
   - 対象者の確認、当選人数の指定、実行（確認画面あり）、過去の抽選記録、直近の抽選の取り消し
4. 設定
   - 条件ルール、選択肢、ステータス、抽選設定
   - ユーザー管理（役割に応じて操作できる範囲が変わる）
5. 取り込み
   - 連携に失敗した回答の再取り込み、旧スプレッドシートのCSV取り込み

### 7.2 配信用画面（配信に映す・表示専用）
- いま「分析中」の1人だけを表示する。XのID、ほかの応募者の情報、課金額は出さない
- 「匿名希望」の人は提督名の代わりに「匿名提督」などと表示する
- 表示項目: 提督名、着任時期、実働期間、プレイ時間、戦果、縛り、目標、相談内容、前回応募との比較（5.5）、前回の分析日
- **ボタンや確認ダイアログを置かない表示専用の画面にする。** 操作は別の画面（7.3）で行う。配信ソフトで画面ごと映したときに、ボタンや「よろしいですか？」の確認、押し間違いが映らないようにするため
- 分析中の人が変わったら、数秒以内に自動で切り替わる
- 配信中の抽選の演出（抽選中…→当選者の表示）もここに出す。外れた人の名前は出さない
- 配信ソフト（OBSのブラウザソースなど）で表示するため、ログイン不要の「配信用の閲覧専用URL」を用意する。推測できない長いURLにし、配信者・運営がいつでも再発行（古いURLを無効化）できる。このURLで見られるのは配信用画面だけで、管理画面やAPIのほかの機能には使えない

### 7.3 配信の操作パネル（配信者・運営、許可された関係者）
配信中に、配信者さん（または手伝いの関係者）が配信に映らない別のタブやスマホで操作する画面。
- いま分析中の人と、次に分析する順の先頭数人（提督名と印）を表示する。XのIDと課金額は出さない（画面共有などで映ってしまう事故に備える）
- 「次の人へ」: 分析中の人を「分析済み」にし、次に分析する順（5.4）の先頭の人を「分析中」にする。抽選を使わないときは、これで配信を進める。重複・条件外の印がある人は飛ばす。押すときに確認を出す
- 「中断」: 配信が終わるなどで分析を途中でやめるとき、分析中の人を「分析予定」の先頭に戻す
- 「元に戻す」: 直前の「次の人へ」を取り消す（押し間違いに備える）。分析済みにした人を分析中に、分析中にした人を元のステータスと順番に戻す
- 配信中の抽選（6.2）と、配信の最後に残りを落選にする操作（抽選を使う設定のとき）
- シミュレータを開くボタン（配信者さんが艦隊を確認するため）
- スマホでも操作しやすい大きさにする

## 8. データの扱い

### 8.1 個人情報
- 集めるのは4.2の項目だけ。メールアドレスや本名は取らない
- 削除依頼があれば、ツールのデータとスプレッドシートの控えの両方から削除する。抽選記録などに残るIDは「削除済み」に置き換える
- 削除依頼は、本人のXアカウントからのDMなど本人だと確かめられる方法でだけ受け付ける。他人になりすました削除依頼で、別の人のデータを消してしまわないため
- 削除の画面では、消える応募の件数と内容を確認してから実行する。実行後に「スプレッドシートの控えからも消す」ことを忘れないよう、手順を表示する
- 削除すると落選回数（6.3）も消えるため、その人が再応募したときは初めての応募として扱われる。削除の画面でそのことを伝える
- 操作履歴には「いつ・誰が削除したか」だけを残し、削除した人の情報は残さない

### 8.3 バックアップ
- 応募データは半永久的に残すため、誤操作やバグでデータを失わないようにDynamoDBのバックアップ（ポイントインタイムリカバリ）を有効にする。費用は段階4の見積もりで公式の料金ページから確認する
- スプレッドシートの共有範囲は運営に限定する

### 8.2 既存応募の取り込み
- 今のスプレッドシートにある応募もツールに取り込む
- 旧スプレッドシートの列構成は未定。「列と新項目の対応表」を渡せる汎用のCSV取り込み機能として作り、列構成が決まってから対応表を用意する
- 対応する項目がないものは空欄にし、「旧フォームの版」として記録する
- 旧フォームの応募者は新しい取り扱い（無期限保管・比較）に同意していないため、Xなどで取り扱い変更を告知しておくのが望ましい

## 9. 技術構成

| 領域 | 採用 |
|---|---|
| バックエンド | Java 21、Spring Boot 4、Gradle |
| API定義 | OpenAPI 3.1（定義を先に書き、サーバーのインターフェースと画面のAPIクライアントを生成する） |
| 実行環境 | AWS Lambda（SnapStartでコールドスタート対策）＋API Gateway |
| データベース | DynamoDB |
| 画面 | React＋TypeScript、S3＋CloudFrontで配信 |
| ログイン | Amazon Cognito（運営・配信者・関係者のグループ） |
| フォーム連携 | Googleフォーム＋Apps Script（送信時トリガー） |
| インフラのコード化 | AWS CDK（Java） |
| CI | GitHub Actions（ビルド、テスト、OpenAPI定義のチェック） |

- 想定費用: 月0〜750円程度（2026年時点の一般的な料金からの概算。実見積もりではない）。AWS Budgetsで月1,000円などの上限アラートを設定する
- 時刻は日本時間で表示し、保存はUTC

## 10. 保守性・拡張性の方針
- 選択肢・ステータス・条件ルール・抽選設定はコードに直書きせず設定データとして持つ。選択肢を変えても過去の回答はそのまま残す
- 応募には「フォームの版」を記録し、質問項目が増減しても古い応募を読める
- OpenAPI定義を唯一の正とし、バックエンドと画面の型はそこから生成する
- バックエンドは層を分ける（API／業務ロジック／データアクセス）。DynamoDBへのアクセスは差し替え可能にする
- 重複判定・条件外チェック・抽選の重みづけは差し替え可能なルールとして実装し、単体テストを書く
- 操作の履歴（ステータス変更、抽選、設定変更、削除）を残す

## 11. 未決事項

- 応募者に向けて順番や抽選結果を公開するか（例: 匿名の順番表）。今は対象外（1.3）だが、応募が殺到すると「自分は何番目か」の問い合わせが増える可能性がある

## 付録A: 制空権シミュレータURLの読み取り（将来の拡張用の調査結果、2026-10-02）
制空権シミュレータ（noro6/kc-web）のソースコードで確認した内容。現時点では実装しない。
- 「共有URLを生成」で出るのは短縮URL。転送先は `https://noro6.github.io/kc-web?data=...` の長いURL
- `data` は編成データ（JSON）を標準の lz-string（compressToEncodedURIComponent）で圧縮したもの
- 中身は艦・装備のIDと改修値・熟練度・レベルなどで、名前は入っていない（名前への変換にはマスタデータが必要）
- 内部形式は公式な仕様ではないため、シミュレータ側の更新で変わる可能性がある
